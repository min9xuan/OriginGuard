# M5.1 本地 Qwen3-VL 多模态 Planner

## 目标

这一阶段把 Agent Harness 的固定 Fake Planner 替换为“可切换”的真实本地 Planner，同时保留 Fake 模式作为稳定回归基线。Qwen3-VL 只负责选择调查 Skill 和说明原因，不直接签署 AIGC 真假结论。

## 本地模型

- 主模型：[Qwen/Qwen3-VL-4B-Instruct-GGUF](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct-GGUF) 的 `Q4_K_M`，约 2.50 GB。
- 视觉投影：同一官方仓库的 `mmproj Q8_0`，约 454 MB。
- 推理运行时：[ggml-org/llama.cpp](https://github.com/ggml-org/llama.cpp/releases) Windows CUDA 12.4 包。
- 文件位置：`.runtime/models/qwen3-vl-4b-instruct-gguf` 与 `.runtime/llama.cpp`，整个 `.runtime` 已被 Git 忽略。

8GB RTX 4060 Laptop 的默认参数是 4096 上下文、单并发、256 batch、128 ubatch、最多 896 像素输入边长。主模型使用 Q4_K_M、视觉投影使用 Q8_0，是为了给 KV Cache 和运行时保留显存空间。

## 数据流

```text
AgentTaskService.run()                 // 校验任务、案件状态、租户与调查员身份
  -> AgentContextBuilder.build()       // 组装案件、关联媒体和人工证据计数
  -> LocalQwenPlanner.plan()           // 读取租户 RAG 指引与首张案件图片，调用本地 Qwen
  -> AgentPlanValidator.validate()     // 校验 Skill 白名单、版本、去重、必选 Skill 和预算
  -> AgentPolicyEngine.requireCanRun() // 对每个 Skill 再做权限、案件状态与 Tool 白名单检查
  -> AgentTool.execute()               // 执行真实确定性媒体工具或 RAG 工具
  -> Observation / Retrieval           // 分开持久化事实证据与知识检索结果
  -> Checkpoint / Trace                // 保存可恢复检查点与审计执行轨迹
```

Planner 的 RAG 输入只来自当前租户已发布知识。检索文本在系统提示中被明确标记为不可信参考资料，模型输出还必须通过服务端白名单校验，因此知识库中的提示注入文本不能直接变成任意 Tool 调用。

## 运行

```powershell
docker compose up -d postgres minio
.\scripts\start-model-api.ps1
.\scripts\start-qwen-vl.ps1
```

启动 Java 后端：

```powershell
.\scripts\start-server-local-qwen.ps1
```

脚本只为当前后端进程设置真实 BGE 与 Qwen Planner 环境变量，不会修改 Windows 永久环境变量。

若不设置 `AGENT_PLANNER_PROVIDER`，默认值是 `fake`，无需启动 Qwen 服务。

## 当前边界

- Qwen3-VL 目前只看案件中的首张图片；多图批量视觉规划留到后续迭代。
- Planner 选择现有四个确定性 Skill，还没有可调用的真实 AIGC 分类器或篡改定位模型。
- Planner 生成的是调查方案，不是最终裁决；审核员仍需基于正式案件证据人工决定。
- Trace 记录模型、提示版本、图片尺寸、引用文档 ID、Token 用量和选择结果，不保存图片 Base64 或完整提示词。
