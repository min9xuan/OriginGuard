# M3.1 真实媒体与基础取证 Tool

## 目标

M3.1 保留确定性的 Fake Planner，将 M2.1 的 Mock Tool 替换为会读取真实媒体字节的受控 Tool，使 Agent Observation 首次来源于真实对象存储和文件分析。

```text
浏览器计算 SHA-256
→ multipart 上传 JPEG/PNG
→ 服务端魔数、MIME、解码、尺寸与 SHA-256 复核
→ MinIO 私有对象存储
→ 案件关联 STORED 媒体
→ Fake Planner 选择 inspect_media_content@1.0.0
→ media.inspect_basic_forensics 从 MinIO 读取字节
→ BASIC_MEDIA_FORENSICS Observation + Checkpoint + Trace
```

## 上传边界

- 仅接受 JPEG 和 PNG 文件签名，不相信扩展名；
- 声明 MIME 必须与魔数一致；
- 单文件最大 25 MB；
- ImageIO 必须能够解码，解码后不超过 40MP；
- 浏览器 SHA-256 必须与服务端重新计算结果一致；
- 租户内继续按 SHA-256 去重；
- 对象键使用 `tenantId/assetId`，不拼接原始文件名；
- 原始文件通过需要 `asset:read` 的接口返回，并设置 `Content-Disposition: inline` 和 `X-Content-Type-Options: nosniff`。

旧版只登记元数据的资产保持 `REGISTERED`，没有伪造对应对象；只有新上传资产为 `STORED`。

## 基础取证结果

真实 Tool 为每条媒体输出：

- 实际读取字节数；
- 检测 MIME；
- 宽高；
- 重新计算的 SHA-256 及其与登记值是否一致；
- 64 位 difference hash（dHash）；
- 限量 EXIF/图片元数据摘要；
- C2PA 状态 `NOT_CONFIGURED`；
- 明确的工具局限性。

## 不代表什么

哈希一致只能说明“当前读取的对象与登记时字节一致”，EXIF 缺失也不能说明内容伪造，dHash 不是 AIGC 检测器。因此 M3.1 结论继续使用 `INCONCLUSIVE`，不得展示为“AI 生成”或“真实”。

## 验证

集成测试使用隔离 PostgreSQL 和 MinIO，程序生成真实 PNG 后验证：V1–V5 迁移、multipart 上传、伪装文件拒绝、授权原图读取、Tool 读取真实字节、4×3 尺寸、SHA 一致、Observation、Checkpoint 与 Trace。

## 下一步

下一纵向切片应把 `BASIC_MEDIA_FORENSICS` Observation 作为证据候选呈现在案件页面，由调查员接受或拒绝；接受后生成带 `agentTaskId / observationId / toolVersion` 来源的正式证据，审核员可在同一页面查看媒体、证据摘要和 Trace。
