# M1.1 媒体记录与案件骨架

## 目标

建立后续证据、算法、Agent、人工审核和报告共同依赖的业务主干，同时保持系统在不接 AI 时仍能运行。M1.1 不上传文件内容，只登记媒体元数据和浏览器计算得到的 SHA-256。

## 已实现

### 媒体记录

- `media_asset` 按租户保存文件名、MIME、大小、SHA-256、创建人和登记时间；
- `(tenant_id, sha256)` 唯一约束防止同租户重复登记；
- 浏览器使用 Web Crypto API 在本地计算 SHA-256；
- 调查员可以登记，调查员、审核员和管理员可以在当前租户内查看；
- 跨租户资源统一返回 404，避免泄露资源是否存在。

### 调查案件

- `investigation_case` 保存案件编号、标题、描述、优先级、状态、负责人、版本和时间；
- `case_asset` 建立案件与媒体的多对多关系；
- 创建者自动成为当前调查负责人；
- 调查员可创建、编辑草稿/驳回案件和关联媒体；
- 审核员与管理员在 M1.1 只有案件读取能力；
- 列表、详情和关联查询都强制带当前 `tenant_id`。

### 状态机

完整领域状态定义为：

```text
DRAFT → READY → INVESTIGATING → WAITING_REVIEW
                                  ├→ CONFIRMED → ARCHIVED
                                  └→ REJECTED → INVESTIGATING
INVESTIGATING → FAILED → INVESTIGATING
```

M1.1 对用户开放到 `WAITING_REVIEW` 为止：

- `DRAFT → READY`：必须至少关联一个媒体记录；
- `READY → INVESTIGATING`：由案件创建者或被分配调查员执行；
- `INVESTIGATING → WAITING_REVIEW`：额外要求 `case:submit`；
- 审核、驳回、确认和归档留给后续人工审核里程碑。

### 一致性与审计

- 更新案件、关联媒体和状态变更都携带 `version`；
- SQL 使用 `WHERE version = :expectedVersion` 条件更新；
- 冲突返回 `409 CASE_VERSION_CONFLICT`，前端重新加载最新数据；
- `audit_log` 追加记录媒体登记、案件创建、编辑、媒体关联和状态变化；
- 审计记录不提供更新或删除接口。

## API

```text
POST /api/v1/assets
GET  /api/v1/assets
GET  /api/v1/assets/{assetId}

POST  /api/v1/cases
GET   /api/v1/cases
GET   /api/v1/cases/{caseId}
PATCH /api/v1/cases/{caseId}
POST  /api/v1/cases/{caseId}/assets
POST  /api/v1/cases/{caseId}/transitions
GET   /api/v1/cases/{caseId}/audit
```

完整请求与响应定义见 `packages/api-contract/openapi.yaml`。

## 数据库迁移

`V2__media_and_investigation_case.sql` 创建：

```text
media_asset
investigation_case
case_asset
audit_log
```

## 自动化验证

后端集成测试覆盖：

- 媒体登记、案件创建、媒体关联和审计读取；
- 同租户 SHA-256 重复冲突；
- 管理员与审核员只读；
- 跨租户案件和媒体隐藏；
- 乐观锁过期版本冲突；
- 无媒体不能进入 READY；
- 禁止跳过状态；
- 合法状态连续推进。

前端测试覆盖权限集合判断和 M1.1 状态按钮映射，并执行 TypeScript 类型检查与 Vite 生产构建。
