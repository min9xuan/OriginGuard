# M4.1 RAG 第一版

## 完成范围

- 管理员使用 `knowledge:upload` 创建 Markdown/纯文本草稿，使用 `knowledge:publish` 发布。
- 发布时按最多 800 字符、120 字符重叠进行确定性切片。
- 每个 Chunk 写入 PostgreSQL `tsvector` 与 pgvector `vector(64)`，并保存文档版本和顺序。
- 查询严格限定 `tenant_id`、`PUBLISHED` 状态和当前发布版本。
- 混合分数为 `0.70 * cosine similarity + 0.30 * FTS rank`。
- Fake Planner 增加 `retrieve_forensic_guidance` Skill，通过受控 Tool 生成独立的 Knowledge Retrieval 与 Citation 记录。
- 引用包含文档 ID、标题、类型、发布版本、Chunk ID、顺序、原文片段和三类分数。
- RAG 结果是 Agent/LLM 的知识上下文，不是案件 Observation，也不能直接纳入正式证据。

## 数据流

```text
管理员录入草稿
→ 发布
→ KnowledgeChunker 切片
→ LOCAL_DETERMINISTIC_HASH_V1 生成 64 维向量
→ PostgreSQL 保存 tsvector + vector

调查员运行 Agent
→ Fake Planner 选择 retrieve_forensic_guidance
→ Policy 校验案件状态、角色和 knowledge:read
→ rag.retrieve_forensic_guidance
→ 租户 + 已发布版本过滤
→ FTS/pgvector 混合排序
→ AgentKnowledgeRetrieval + AgentKnowledgeCitation
→ Trace / Checkpoint / 调查方案知识上下文
```

## 有意保留的边界

第一版没有调用 LLM，也没有下载 Embedding 模型。本地 Feature Hashing 向量只能验证向量存储、过滤、混合召回、引用和 Agent Harness 链路，不能宣称达到生产语义检索质量。媒体工具产出的案件事实保存在 Observation；知识检索结果独立保存，后续供 Planner/Synthesizer 使用。下一版可在保持 `KnowledgeRetriever` 接口和引用结构不变的情况下替换为真实 Embedding，并加入离线检索评测与 Reranker。
